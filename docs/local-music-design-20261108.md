# 本地音频库：安卓讨论方案

状态：2026-11-08，用户将范围从本地音乐扩展为音乐、音声、有声书、录音等常用音频，并确认保留副本/引用两种模式，倾向复制，同时要求“小而精”。数据与导入后端见 [阶段交付](backend-local-audio-delivery-20261108.md)，同一播放服务/独立续播接入见 [播放接续](backend-local-playback-delivery-20261108.md)，入口见 [合同](frontend-backend-contract-local-audio.md)。本文保留方案及后续目标，不代表正式前端或实机已经验收。沿用原文件名以保留现有链接。定时停止服务见 [合同](frontend-backend-contract-sleep-timer.md)。

## 用户确认与实现约束

两种导入方式都提供，默认 `COPY`：复制成功后可由用户自行删除原文件；Musxi 不自动删除源文件。`REFERENCE` 只保存系统授予的读取权限和文件引用。实现优先 Android 系统 API 与现有 Media3/协程，不新增数据库框架、FFmpeg/转码库或另一套播放器；以实际 APK 增量核对体积。界面保持常用操作直接、进阶选项按需展开，正式视觉由 CC 接续。

## 用户场景与推荐体验

用户自行下载喜欢的音声，在 Musxi 创建一个文件夹，导入并命名，平时专门在这个文件夹听。因此本地音频应有独立入口，不要求每个文件具备歌手、专辑或平台歌曲身份；用户自行下载后导入也不等于本轮要新增下载器。

建议流程：创建“睡前音声” → 多选音频或关联手机已有目录 → 修改显示名、调整顺序 → 播放与添加时间书签 → 定时停止 → 下次继续上次文件和位置。

“继续这个文件夹”和“从第一条播放”应有清晰不同的行为。前者回到该文件夹上次条目及其进度；后者从首条起播。第一版先支持单层自建文件夹，任意嵌套分类后续再定；若源目录有子目录，导入时明确是否包含，不静默展开整个存储。

## 应用文件夹与系统目录

推荐 Musxi 里的“文件夹”默认是应用内逻辑分组：可以把分散在几个真实目录的文件放在一起，同一文件也可加入多个分组而不复制音频。其名称、成员、顺序和封面由 Musxi 保存。真实目录是文件来源和系统授权范围，不强制一一对应到应用文件夹。

这两层分开后，用户整理“睡前”“喜欢的片段”“某作品”，不需要移动手机上的原文件。显示名修改只改应用元数据，原文件名、内嵌标签和所在位置仍保留；重新扫描不得冲掉用户显示名、手动顺序、进度和书签。显示名建议按用户覆盖名 → 有效标签 → 文件名回退，并提供按文件名显示的偏好，避免一批无意义的内嵌标题影响音声排序。作者、系列、介绍均可空。

成员关系与音频本体分开：“从文件夹移除”只移除该成员；“从本地库移除”处理所有成员关系与授权引用；不以这两个动作删除用户原始音频。目录刷新发现源文件消失时保留条目及整理数据：引用标记缺失，Musxi 副本仍可播放，不按扫描差集直接删除用户记录。

## 导入与存储

| 方式 | 用户行为 | 建议边界 |
| --- | --- | --- |
| 选择文件 | 多选几个已下载音频，放进当前应用文件夹 | 默认复制到 Musxi，可显式选择只授权引用；不自动删除源文件 |
| 关联目录 | 选择手机某个音声目录，保存关联后手动刷新发现新增文件 | 后端已接；子目录范围、扫描进度、逐项结果和同源重新授权，正式页面待接 |
| 保存一份到 Musxi | 复制到应用管理的存储，原下载文件删除后仍可播放 | 用户已确认纳入首版并倾向默认；流式复制、空间检查、取消清理，卸载会删除应用副本，导出另接续 |

用户后续已确认两者均提供，并倾向复制。当前实现默认复制，不转码；在本地库内相同内容复用一份副本。引用模式仍可显式选择，导入结果需明确“引用原文件”，不能让用户误以为音频已另存。

目录关联采用用户显式刷新，不承诺实时监听所有文档提供方。刷新只更新来源元数据、发现新增和记录缺失；已手动移出的成员不会被加回，人工整理结果独立保存。目录来源记录与音频、成员分开，取消关联只删来源记录，保留所有已导入条目和归属。

使用 Android 系统文件选择器与 SAF 授权，不先申请全盘权限或静默扫描。目录授权可覆盖其子文件；逐文件授权控制数量，并在无剩余引用后释放。提供方不支持持久读取时明确提示重新选择。系统限制不可选择的目录不能靠裸路径绕过。SAF 也可能返回云文档，content URI 本身不保证离线可用。

文件身份使用应用稳定 ID，授权 URI / documentId 是来源关联依据，文件名不是主键。相同文档经不同目录授权打开可尝试归一；不同提供方的改名/移动行为不一致，不能保证 URI 或 documentId 永久稳定。无法自动确认时提供“重新关联”，保留原音频 ID、显示名、分组、进度与书签。不同录音不能仅按同名或同大小合并；COPY 在流式复制时计算内容标识，REFERENCE 不为常规导入或播放全量哈希。文件内容被替换时按可用的大小/修改时间提示识别版本变化，提示不可靠的限制见现行合同。

## 长音频与播放行为

需要同时保存三种状态：

- 每条音频的播放位置、是否自然播完、最后播放时间；同一音频在多个文件夹内默认共享进度。
- 每个文件夹上次播放的成员；切去其他本地分组或线上音乐后仍能回到原条目。
- 当前活动队列和播放器位置；这是服务恢复状态，不能代替前两者。

例如音声 A 听到 23:18，随后切去听歌，回到“睡前音声”选择继续，仍应回到 A 的 23:18；改显示名和重新扫描不重置该位置。另设“从头播放”；自然播完的文件再次点击默认从头重听，不恢复在末尾。

播放偏好建议按文件夹设置“继续上次 / 从头播放”，初始偏好可随内容用途选择，不强制用户给每个文件填分类。音声、有声书偏向续播，音乐偏向从头。首版优先加入简单命名时间书签，例如“喜欢的片段，18:42”；自动回退几秒、A–B 循环、复杂章节和跨文件片段可后续增加。

音声常包含刻意留白和双耳立体声：默认保持原速与声道，不自动开启静音跳过、增益、单声道或额外音效。倍速、回退等适合有声书的偏好应可选，不因“非音乐”而统一施加。

通知、耳机/蓝牙、音频焦点、后台播放和既有三种定时策略沿用同一个播放服务。“播完当前曲”在本地语境应表达为“播完当前音频”；数小时音频下，到点立即停与到点再播完的差别要清楚。播完整个文件夹停止、音量渐弱属于新增建议，现有定时后端没有这些模式。

## 格式、歌词与文件异常

首轮目标样本包括 MP3、M4A/AAC、M4B、FLAC、OGG/OPUS、WAV，实际可播仍取决于容器、编码、Media3 提取器与设备解码器。M4B 能播放与其内嵌章节可浏览是两个验收项，不能等同。受保护文件、CUE、DSD、压缩包直接导入及视频播放另评估；用户本轮要求是常用音频，不据此扩成通用视频播放器。

导入不能只依赖 MediaStore 的 `IS_MUSIC=true`，否则录音、播客等会被漏掉；文件选择器对 MIME 标注不完整的音频需有可验证的补充选择路径。元数据/封面读取限量并在后台进行，标签读取失败不阻塞其余文件导入；无标题、歌手、专辑仍是合法条目。

原文件删除/移动、SD 卡临时卸载、授权撤回、云文档离线应分为不同可用状态，保留重试或重新关联入口。不能把单次扫描失败当作空目录，也不能自动拿平台同名歌替换本地音声。音频索引、读取授权、书签和进度不属于可随意清理的普通缓存。

本地音乐歌词可沿用 LRC 解析模型：目录授权时读取同目录同名 LRC；单音频授权不能推定有权读取旁边文件，需另选歌词或目录。内嵌歌词另核查解码能力。音声不必有歌词，不自动上传或发送平台搜索匹配；后续手动绑定线上歌词时复用显式预览、保存与偏移流程。

## 与现有安卓代码的衔接

下列是已核实的播放服务边界；本轮数据与导入实现不放宽这些限制：

- `Platform` 只描述酷狗、QQ、网易账号；`MediaKey`、`PlaybackQueue.accountGeneration`、`QueueSources` 都依赖平台/账号。引入明确的平台歌曲 / 本地音频来源，在播放边界适配，不建立假 LOCAL 账号。
- `PlaybackSourcePolicy` 只允许三平台 ID 与网络地址白名单。当前服务使用 HTTP DataSource 包装 opaque resolver；本地另设受控 content 解析与本地 DataSource，不放松网络规则、不让 UI 或媒体控制器持有原始路径。
- 平台播放日志、最近播放、封面和歌词按平台/账号分区，本地使用独立存储。第一版本地与平台队列分别管理，不做混合队列；同一播放服务在切换来源时保存各自状态。平台退出登录不影响本地库。
- 平台 `FilePlaybackJournalStore` 保留原有 24 小时校验；本地模型、服务位置与独立队列恢复日志采用有界的长时长校验，上限 366 天，不因平台旧上限截断长录音。

建议的数据职责（名称为讨论用，不是已发布合同）：

| 数据 | 职责 |
| --- | --- |
| 本地音频 | 稳定 ID、来源引用与版本、扫描元数据、用户覆盖、可用状态 |
| 应用文件夹及成员 | 名称/封面/播放偏好、音频归属、手动顺序、导入来源 |
| 文件授权 | 持久目录/文件授权与引用关系，不与应用文件夹绑定为同一个对象 |
| 播放进度及文件夹游标 | 每音频位置与播完状态、每文件夹最后成员 |
| 时间书签 | 音频 ID、时间点、用户名称；不绑定易变化的文件名 |

领域模型、持久化、Android 导入与目录刷新、同一播放服务和公开状态已接入。CC 暂缓不阻塞后端后续工作；系统选择器入口、正式整理页面及体验仍需前端接线。

11-09 后端另已接用户手动选中条目的轻量来源检查，与播放前探测共用；不全量读音频或新增后台扫描。检查缺失、权限、大小／修改时间及首字节可读性，保留整理／进度数据；实现和边界见[当轮交付](backend-local-source-check-delivery-20261109.md)，接口以[合同](frontend-backend-contract-local-audio.md)为准。

## 分期与验收建议

当前已接最后本地队列的持久化和服务启动暂停恢复，含临时编辑、循环及实际随机顺序，详见[恢复接续](backend-local-resume-delivery-20261108.md)；持久目录关联与手动刷新见[目录交付](backend-local-directory-delivery-20261108.md)；原始音频导出与整理备份／合并恢复见[传输交付](backend-local-transfer-delivery-20261108.md)；元数据检索、筛选分页、批量整理与全文件夹规则排序见[11-09 交付](backend-local-organization-delivery-20261109.md)。本方案其他前期描述保留设计背景，现行接口以[合同](frontend-backend-contract-local-audio.md)为准。整理备份不含音频和系统授权，一键媒体迁移、倍速/AB/章节等增强另续。

第一阶段目标是完整可用链路：创建/改名应用文件夹、音频多选导入与目录关联、显示名、自然数字排序和手动顺序、后台播放、每条进度与文件夹继续、简单时间书签、不可用状态与重新关联。两种导入模式均纳入，默认复制。数据/单次导入/持久目录关联与刷新及同一服务本地播放、文件夹续播后端已接入；正式前端与真实听音仍待接续。

第二阶段再完善倍速与快进/快退偏好、A–B 循环、内嵌章节、自定义封面、导出与整理数据备份。后续系统曲库扫描不替代用户创建的本地分组。

验收应覆盖：一条无标签录音也能导入；编号 1/2/10 自然排序；同文件重复导入不复制；改显示名后重扫/重启仍保留；两个文件夹共享文件但各自记住最后成员；本地与线上来回切换后续播；暂时失效不删书签、重新关联后保留进度；暂停/进程恢复与定时停止；大文件及超过 24 小时的时长边界。格式、长后台、耳机和真实听音以本轮实际安装包和设备样本验收，不拿参考项目能力代替 Musxi 结果。
