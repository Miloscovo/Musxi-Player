## 确认并修复的酷狗问题

同一会员账号，保存队列前 12 首的音质菜单全部只有标准档。debug 仅输出固定阶段／错误类别的真实诊断确认：

1. 基础 `/v5/url` 的无损响应返回另一音质文件 hash，既不等于请求 hash，也不是现有 `std_hash` 特例，原代码直接拒绝 `identity`，没有进入官方授权链。
2. 独立执行既有 privilege → user_verify → authorization → tracker URL 链后，同一录音的无损变体可被证明，载荷位率／格式／hash 校验通过。实际 `valid` 是数字、`auth` 是字符串，不支持此前“布尔 valid 导致误判”的猜测，没有放宽这些字段。
3. 官方无损 URL 返回项目现有允许的两个 HTTP CDN 域名；原授权解析强制转换 HTTPS，两个候选均 `ssl_peer`。原响应中的 HTTP 地址实测均 HTTP 206。

`KugouLibraryApi` 现对带固定 `audio_variant_hash` 标记的基础响应身份差异，允许再次独立执行既有官方授权链；不接受基础错 hash 的 URL。只有原曲 privilege 关系、唯一音质变体、专辑和授权响应 hash 等既有校验全部通过才播放。其他 identity、网络／风控错误不因此开启新回退。

授权普通无损沿用现有 HTTP 兼容规则：优先 HTTPS，只保留官方原响应中的 `fs.youthandroid2.kugou.com`、`fs.youthandroid.kugou.com` 原始 HTTP 地址；不新增域名、不关闭证书校验、不从 HTTPS 合成 HTTP。Hi-Res 不扩大这一规则。前端菜单／账号／质量偏好模型不变。

新增 3 项回归测试：基础变体不匹配后独立授权成功及无授权拒绝；无法证明原曲变体时不得播放；授权 FLAC 的限定 HTTP 兼容与 HTTPS-only／Hi-Res 不降级。失败授权仍保留原基础错误并附固定类别，不导出私有响应。
