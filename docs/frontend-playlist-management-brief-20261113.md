# 给 CC：歌单操作前端需求单

日期：2026-11-13。项目主目录：`C:\text\Musxi-Player安卓`。

本需求单供用户后续交给 CC 实施，范围是三平台曲库中歌单本身的**创建、改名、移动排序、删除整单**。保留既有红心及“收藏到”功能。当前后端已可接线，正式页面仍需同包验收。

接口依据为[歌单管理合同](playlist-management-contract.md)、[目录与排序合同](backend-playlist-library-management-20261113.md)、[酷狗生产删除接入](backend-kugou-playlist-delete-20261113.md)。本需求单补充11-06[首版需求](frontend-playlist-brief-20261106.md)中的后续能力，旧文“不接新建／改名”的阶段范围不限制本次；不要重复重做已由用户验收的“收藏到”面板。

## 一、用户操作范围

| 操作 | 页面行为 |
| --- | --- |
| 新建歌单 | 当前平台曲库直接新建空普通歌单，不必先选歌曲；成功后显示服务器返回的真实歌单 |
| 改名 | 本人有权限的普通歌单菜单进入命名框，保留原名并显示提交状态 |
| 移动排序 | 提供移动到普通区域最前、拖动调整、移到最后、恢复平台默认顺序；排序只在Musxi保存 |
| 删除歌单 | 本人有删除权限的普通歌单提供整单删除，明确确认后提交；允许非空歌单，不先清歌 |

菜单入口沿用当前曲库的长按／更多交互与既有视觉风格。排序可以覆盖非“我喜欢”的普通／收藏展示行，不代表对它们具有远端改名或删除权限。“我喜欢”固定最前，不能拖动、改名或删单。

本次移动是**改变歌单在Musxi曲库中的展示位置**，不转移平台、不移动歌曲，也不同步官方客户端的歌单排序。

删除确认应包含平台和歌单名称，明确“删除整个歌单，包含其歌曲列表关系”。这是平台远端操作，不能把它包装成只隐藏Musxi卡片。歌曲本身及其他歌单不随之删除，已有播放继续保留。

## 二、统一目录接线

入口为 `app.playlists`，以下命令和回调在主线程使用，后端负责网络与磁盘调度。页面不接触平台凭证、原始响应或排序文件。

```kotlin
val catalog = app.playlists.catalog(platform)
// 页面订阅 catalog.state；进入调用 open()，离开调用 cancel()。
```

| 数据／操作 | 使用方式 |
| --- | --- |
| 列表 | 显示 `catalog.state.items`，后端负责跨页合并及本地排序 |
| 生命周期 | `open()`／`cancel()`；切换平台切换对应catalog，废弃旧页面回调 |
| 主动刷新／分页 | `refresh()`／`loadMore()`，以 `loading / nextOffset / complete` 展示状态 |
| 顺序版本 | `revision`，拖动开始固定本次版本 |
| 本地排序状态 | `customOrder / savingOrder / storageError`，分别表示自定义顺序、保存中及存储异常 |
| 平台写入互斥 | 收集 `app.playlists.busyPlatforms`，禁用同平台冲突提交并防双击 |

不要再把旧browser的累积页拼入新catalog；详情／曲目页继续使用其原接口，不能拿曲目分页充当歌单目录。分页和排序不由UI重算服务端offset，不能用已加载的部分列表证明远端不存在。

加载失败、空目录、未登录／身份不可用、缓存内容及顺序存储失败应有相应反馈；读取失败不能显示成“账号没有歌单”。

## 三、能力与行权限

先读 `app.playlists.capabilities(platform)` 判断平台入口能力；打开歌单菜单时读取 `managementInfo(key, callback)`，使用返回的：

- `target: EditablePlaylist`：本次改名／删除使用的完整目标，含账号代次。
- `canRename`：是否显示可用改名操作。
- `canDelete`：是否显示可用删除操作。
- `canUnfollow`：取消收藏权限，属于其他操作，不能当作删除权限。

权限尚未读到时不能先提供可点击的远端写入按钮。收藏他人歌单与删除本人歌单须区分；不能用“能改名”推导“能删除”。后端写前仍会重新核实，本次菜单提示不等于永久授权。

三平台当前创建／改名／删除均有实现，具体行可能因权限或缺少必要元数据而拒绝；酷狗 `delete=true` 已正式开放，不能沿用早期资料的禁用状态。网易云／酷狗整单收藏写入缺口仍保留，本需求单不扩大订阅功能。

切号或账号代次改变后，关闭旧菜单／输入状态并重新读取。不得构造目标ID、丢弃 `accountGeneration` 或用重名匹配替代精确身份。后端错误类别映射为用户能理解的提示，不直接展示内部reason、私有响应或异常链。

## 四、新建与改名

| 操作 | API | 成功后的处理 |
| --- | --- | --- |
| 新建空歌单 | `createPlaylist(platform, name, callback)` | 使用返回的 `EditablePlaylist` 及真实标题；后端失效目录并将已确认新建放到普通区域最前，页面观察catalog刷新 |
| 改名 | `renamePlaylist(target, name, callback)` | 刷新真实列表／详情；排序按ID保留 |

名称非空、无控制字符，通用边界最多80个Unicode code point；QQ改名另有限制：去首尾空格后最多20个UTF-16 code unit。名称校验提示需跟随后端规则；平台仍可能拒绝或调整名称，最终展示返回／刷新后的实际标题。不要假定重名一定失败。

提交中防重复，失败保留输入以便核对。创建／改名都可能发生“平台已接受但响应未确认”：**不能在网络失败、超时或not_confirmed后自动重发**。先刷新让用户核对，不能按标题猜创建结果对应ID，也不能为了补偿创建而自动删除。

如果涉及已有“新建并加入”入口，继续使用 `createPlaylistAndAdd(song, name, callback)` 并分别处理“创建成功”和“加歌结果”。添加失败仍展示已创建歌单，后续只向返回目标补加，不得重新创建。它不是本次曲库空创建的必备前置步骤。

## 五、删除整单与未知结果

使用 `managementInfo` 返回的target，经用户确认后调用 `deletePlaylist(target, callback)`。**外层 `Result.success` 只表示流程完成，不能直接显示删除成功。** 必须检查 `PlaylistDeletionResult.status / confirmedAbsent / error`。

| 返回 | 页面反馈 |
| --- | --- |
| `APPLIED`且`confirmedAbsent=true` | 已确认删除，按后端刷新结果移除展示；若当前详情正是该目标，退出或显示已删除状态 |
| `UNCHANGED`且`confirmedAbsent=true` | 目标原已不存在，刷新列表，按已不存在处理 |
| `FAILED` | 展示失败原因；`confirmedAbsent=false`表示回读仍在，null表示缺席状态未核实，不能都称为“确认未删除” |
| `UNKNOWN` | 提示“结果未确认，请刷新核对”，不自动重复删除、不当作尚未删除 |
| 外层 `Result.failure` | 处理忙碌、权限、账号变化、能力等前置拒绝；不能当作成功 |

后端最多写一次并做完整读回，丢响应仍先核对；页面不另加补偿写入。取消弹窗可在提交前中止；已发出后离页只是停止等待，不能承诺撤销。

删除确认后，后端会失效相关目录／详情、移除本地排序记录并取消未接受的该歌单播放补载。**已经接受的播放队列继续保留**，前端不要暂停、清空、Replace或重建队列来刷新页面，也不要改变歌曲红心或其他歌单。

## 六、本地排序与冲突

| 动作 | API／限制 |
| --- | --- |
| 移到普通区域最前 | `catalog.moveToStart(key, expectedRevision, callback)`；“我喜欢”仍在最前 |
| 拖动到某行之前 | `catalog.move(key, before, expectedRevision, callback)`；锚点须为已加载的非“我喜欢”行 |
| 移到最后 | 同一move入口，`before=null`；必须先满足 `state.complete=true` |
| 恢复默认 | `catalog.resetOrder(expectedRevision, callback)`；恢复平台列表顺序 |

拖动开始保存 `state.revision`；刷新、切号、加载更多或保存结果导致revision变化时取消本次拖动。后端返回conflict后刷新并让用户重新操作，不能偷偷换新revision自动重试旧手势。拖动过程可有临时预览，持久结果以回调及新state为准；失败恢复已确认顺序。

未加载完整时仍可向已加载行之前移动或移到最前；“移到最后”应禁用或先让用户加载完整，不能将“当前页末尾”冒充全列表末尾。`savingOrder`期间避免重叠保存；存储失败不能提示已保存。

排序按平台、账号独立保存，重启及同账号重新登录后恢复；刷新、清普通缓存和平台退出不删除顺序。账号切换不能沿用上一个账号排序。后端拥有持久化与分页合并，UI不再保存第二套排序副本。

## 七、通用异常与交互

| 类别 | 页面动作 |
| --- | --- |
| `busy` | 同平台有操作进行中，禁用冲突提交并提示稍后 |
| `account_changed` | 废弃旧目标和回调，重新读取当前账号状态 |
| `conflict` | 列表已变化，取消旧拖动并刷新 |
| `incomplete` | 无法证明目录完整；排序时先加载更多，远端操作时按具体失败提示 |
| `storage`／`storageError` | 顺序保存／读取异常，保留已确认数据并提供错误反馈 |
| 权限／不支持／名称非法 | 给出相应提示，不能反复重试同一写入 |
| 网络／超时／结果未确认 | 区分读取失败和写后未知；先刷新核对，不自动重放创建／改名／删除 |

采用当前页面／账号的回调身份检查，离页后不把迟到结果画到另一个账号。保留已确认成功项；目录刷新失败不应反向提示刚才远端操作一定失败。

## 八、验证范围与验收

已有后端证据：QQ／网易云当前生产入口各完成一次空歌单创建及删除闭环；酷狗空创建已核实精确返回ID，且非空普通自建歌单在一次授权探针中整单删除成功，随后相同请求形状接入生产后端并补回归。酷狗生产删除未重复消耗其他歌单；旧QQ创建不确定记录仍保持未知。这些证据不代替本次正式菜单、拖动和复杂账号场景验收。

CC交付需覆盖：

1. 三平台曲库均使用统一catalog，新建／改名／删除入口按能力和行权限提供；“我喜欢”受保护，收藏歌单不误显示本人删单。
2. 创建展示真实标题，改名后目录／详情更新，排序位置保持；名称非法、忙碌、风控和网络失败有反馈，重复点击不会重复提交。
3. 删除有明确整单确认，仅确认缺席才按删除完成处理；FAILED与UNKNOWN可区分，离页不承诺撤销，不自动重试。
4. 拖动、移到最前／最后、恢复默认可用；“我喜欢”固定，分页不完整、revision冲突、保存失败均正确处理。
5. 刷新／重启保留排序，账号隔离，旧回调不能修改新账号页面；现有红心、“收藏到”及已接受播放队列不受影响。
6. 按项目规范做针对性检查及最终 `scripts/verify.ps1`，区分模拟测试、编译通过和用户实机结果。

实现以正式UI及相关测试为主，协议与核心模型问题交回Codex定位，不另写请求链。保留既有未提交改动，构建使用共享锁。真实平台创建／改名／删除验收由届时用户另行指定测试目标与窗口，**历史一次性写入授权和marker不能重用或清除**；本需求单本身不授权操作用户其他歌单。交付列明改动、验证、未完成项，不自动提交、推送或发布。
