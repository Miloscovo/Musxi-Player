## 暂停检查失败与诊断

首轮DSD64通过；首轮DSD128已完整自然结束，91次采样、墙钟45,599ms／推进44,497ms，没有采样到缓冲，但随后暂停位置检查失败，原阶段仍为`failed`，没有覆盖成成功。

原检查在`!playing && !playWhenReady`后固定等300ms，取位置，再等1.5秒比对。原失败未记录两次位置，不能精确还原那次偏差。随后新增仅测试代码的`dsf128_pause_probe`，使用同一owned条目，按100ms左右记录应用状态和主线程MediaController位置，独立诊断观察到：

- 暂停前应用位置1516ms；暂停约46ms后两边均已暂停，预计位置1551ms。
- 约148ms时控制器位置校正到1096ms，应用仍暂存1551ms；约350ms时应用同步为1096ms，此后稳定。
- 两边暂停标志始终为false／false；2秒之后的位置稳定、恢复及10／30／5秒定位通过。

对照实际依赖Media3 1.8.0的`MediaControllerImplBase.pause/setPlayWhenReady/onPlayerInfoChanged`，控制器会先返回预计暂停状态，再接收服务读回。诊断及最终复验均观察到一次位置回校，支持原固定300ms窗口存在时序问题；因首失败没有具体位置记录，不声称已逐帧证明其原因，也不把该失败包装成解码器修复。

最终测试改为**最多3秒等待读数一致并稳定500ms，再连续观察至少1.5秒，误差仍为100ms**。等待中及稳定窗口同时核对控制器与应用均暂停、无错误，记录原始位置序列；超时仍失败。两个倍率在最终测试包下重新从头播完及控制，分别通过。Media3在STATE_ENDED仍可能保留playWhenReady=true，曲末以ended、!playing和结束位置验证，原值保留在JSON。

本轮唯一应用树改动为`app/src/androidTest/kotlin/tech/musxi/player/AudioExpansionDeviceTest.kt`，增加固定64／128短样、诊断和owned复验步骤。没有修改release源文件或新增应用依赖。`PlaybackHost.experimentalDsfDecoding`和公开`DsfPreviewInfo.playbackSupported`继续false。
