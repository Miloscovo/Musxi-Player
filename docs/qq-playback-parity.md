# QQ 桌面与安卓播放能力对照

2026-10-19：当前为代码核对和后续实验设计，没有完成同一账号、同一曲目、同一音质的两端对照，不能宣称已定位或解决会员歌曲差异。

后续用户澄清：QQ《AIZO》在桌面与安卓均无法播放，搜索中第一个同名结果可播（用户推测是网易云）。因此该例尚不证明安卓能力落后于桌面；其他来源的身份、版本与完整时长待核实。已将用户选择其他平台音源、播完接回原歌单确定为下一阶段方向，见 [cross-platform-sources.md](cross-platform-sources.md)。同平台取流差异调查仍保留，不作为当前第一优先级。

## 已确认

- 桌面 `services/qq_bridge.py` 的 `audio()` 调用官方 `get_song_urls()`，支持 128 / 320 / flac；没有完整 purl 或 result 非零时报告“此账号暂无该音质播放权限”。核对文件名、路径和 ekey，不能从当前实现推断普遍解锁会员。
- 桌面 bridge 构造 `Client(device_path=...)`，没有覆盖默认请求平台；固定 qqmusic-api-python 0.8.1 的 Client 默认 ANDROID。取流 UrlGetVkey 没有单独改为 Web，歌曲详情接口则显式使用 WEB。这是请求配置，不是桌面操作系统类型。
- 安卓 `QqMusicApi.cgi()` 使用 WEB 公参，加音乐身份和实际音乐密钥；`QqLibraryApi.audio()` 同样使用官方 UrlGetVkey/CDN 调度，目前只请求标准 MP3_128（M500）。两端 vkey 业务参数都包含 songmid、media_mid 形成的文件名、songtype、uin 和 guid，但请求环境未完全对齐。具体鉴权、设备会话、签名和传输也须逐项核对，不能认为只改一个 ct 即等价。
- 安卓首次一次请求返回 104003；补充歌单后部分曲目播放成功，当前列表第 1 项后来也成功。没有保留可直接比较的同曲版本证据，不能把原拒绝归因为某首歌永久无权限或安卓固有限制。
- 当前自动测试和真实播放只证明部分曲目/当前账号可播，没有验证全量会员目录。未逐首核实试听、完整时长或所有付费音质。

## 建议的受控对照

1. 用户选择 1～3 首桌面确实能完整播放、安卓失败的 QQ 歌曲；先对照同一个账号和当前会员/临时权益状态，不收集或展示凭证。
2. 确认同一 songMID、发行版本及 songtype；不能仅按歌名匹配现场版、翻唱、重录版。诊断只输出相同/不同布尔及固定失败类别，私密标识不进入共享日志。
3. 两端先统一标准 128 音质，在接近时间重新取流，排除旧 URL 或缓存。记录成功阶段：身份验证、详情、vkey、CDN、解码、真实播放；权限拒绝与网络/地址错误分别处理。
4. 核对可播放时长与歌曲完整时长、听音和中后段跳转，必要时实际播完；“进度增长几秒”不能证明完整音频，拒绝把试听当成功。
5. 如果桌面完整成功而安卓失败，再对照请求 profile、公参、音乐会话类型、文件信息和 CDN 兼容。一次只调整一个有证据的差异，用固定 fixture 和真机回归验证，保留其他平台行为。
6. 如果两端同样收到官方权限拒绝，结论应为此账号/此音质本次未获得完整音频；不继续伪装成功、无限重试或无提示替换版本。低音质也需独立可用验证，并告知用户实际音质。

## 产品和验收目标

先证明并修复“桌面当前能完整播放而安卓不能”的具体差异，提高已可用完整歌曲的覆盖率和稳定性。不要把目标写为所有会员歌曲无条件可播；服务器是否发放完整音频地址不由播放器单方面决定。

免费音质、同账号临时权益、另一平台确实开放的同一录音、用户自己的本地音频均应明确标识来源和实际质量。跨平台匹配和本地音乐尚未因此实现，不自动把不同版本当同一首，也不以不明解析服务替代可验证结果。

前端将账号连接、列表刷新、歌曲播放能力分开；权限拒绝提供清楚原因和跳过/重试等合适动作。对尚未核实的失败使用“暂时无法获取完整音频”，避免笼统标“安卓不支持”或自动断开账号。QQ 分页缓存只保存元数据，不保存音频，也不增加账号权限。

2026-10-19 后续实现证据：Android 原 QQ 7 项歌单中的 AIZO 本次明确失败后，真实搜索其他两平台候选，5 秒后选择网易云来源；原 QQ mediaId/索引 0 保留、进度增长，用户确认“声音正常，是预期歌曲”。将替代音频 seek 到曲尾前 1 秒，等待真实结束，自动进入原 QQ 索引 1、实际 QQ 来源播放，候选状态清空。该证据证明跨平台临时来源闭环，不代表 QQ 原曲权限已改变，听音确认也不等于已证明录音文件完全一致或逐秒完整试听。
